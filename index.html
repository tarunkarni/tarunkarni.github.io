Catching ransomware before it locks your files

My M.Tech thesis. A machine-learning system reads the Windows API calls a program makes as it starts and predicts whether it is ransomware, aiming to raise the alarm before files are encrypted. I built the whole pipeline: an automated malware-sandbox lab, 11,000+ behaviour traces from two Windows versions, and a careful comparison of eight detection models.

The data-collection pipeline, the Windows 7 dataset and three rounds of experiments are finished. Final experiments on the Windows 10 dataset and the journal paper are in progress, so the results shown here are preliminary and may change.

The question

Ransomware does its damage once it starts encrypting, so a detector only helps if it decides before that point. Most published detectors react to encryption itself, and many report near-perfect accuracy on complete traces and random splits. This thesis treats earliness as the main question: how many API calls does a model need before it can reliably tell ransomware from legitimate software?

The base paper, Ranker (IEEE TIFS, 2024), detects ransomware early from kernel-level events with hand-designed patterns. I ask a similar question one layer higher, from user-mode API calls, with learned models instead of hand-written rules.

Five research questions

  • RQ1Earliness. How many API calls before a model flags ransomware reliably at a 1–2% false-alarm rate?
  • RQ2Unseen families. Does detection still work on families never seen in training?
  • RQ3Call order. Does the order of calls add anything beyond which calls occur and how often?
  • RQ4Data and shortcuts. How much of the accuracy is explained by shortcuts such as trace length?
  • RQ5Interpretability. Which calls drive the decisions, and do they match known ransomware behaviour?

The pipeline

Each sample runs once in a freshly reset sandbox, and every model is trained and tested on the same prefixes of its calls.

Analysis lab: Ubuntu workstation with isolated Windows VMs

  1. Collect samplesMalwareBazaar, RanDS, VirusShare, public repositories, plus benign software.
  2. Label and dedupeFiles named by SHA-256; family names and aliases normalised (ALPHV to BlackCat, Sodinokibi to REvil).
  3. Run in sandboxCuckoo with KVM/QEMU, Windows 7 or 10, decoy user files, 240 s per run, reset after each run.
  4. Extract tracesAPI-call names, up to 3,000 per run, plus counts and metadata.

ML pipeline: laptop GPU and Kaggle notebooks

  1. Build the dataset11,000+ traces grouped by binary, separate Windows 7 and Windows 10 sets.
  2. Train modelsFour count-based models, four sequence models and two baselines.
  3. Evaluate fairlyThe core of the work: prefixes of 10 to 3,000 calls, grouped 5-fold CV, unseen families, call-order ablation.
  4. Explain and reportSHAP and occlusion; the earliest reliable prefix for each model.

Models compared

Every model sees exactly the same window of calls, so the comparison is fair.

Count-based

  • Gradient boosting (LightGBM)
    Call counts plus window features: which calls occur, how often and roughly when
  • Random forest
    The classic bag-of-calls view, with a 1–3-gram variant
  • MLP
    Non-linear interactions between counts
  • Logistic regression
    A simple linear reference

Sequence

  • 1D-CNN
    Dilated residual convolutions for short local patterns like read, encrypt, write
  • BiLSTM
    Long-range order in both directions, on patches of 4 calls
  • Transformer encoder
    Self-attention between any two calls
  • Hybrid CNN–MLP
    Local patterns plus the overall call profile, fused by a learned gate

Baselines

  • Trace length only
    Measures how much trace length alone gives away
  • Ranker rules
    The base paper's four hand-written file-behaviour patterns

How the evaluation guards against inflated accuracy

  1. Prefix-level retraining: each model is retrained at call budgets from 10 to 3,000, giving an early-detection curve.
  2. Grouped 5-fold cross-validation: all runs of one binary stay in one fold; thresholds are chosen on training data only.
  3. Strict operating points: recall at 1% and 2% false-positive rate, balanced accuracy, MCC and ROC-AUC.
  4. Unseen families: leave-one-family-out, plus harder cross-source and time-ordered splits.
  5. Matched order ablation: global and local shuffles compared with the original order.
  6. Shortcut controls: a length-only baseline, minimum trace length, de-duplication, family-name normalisation and masking of GUI calls.
  7. Streaming simulation: score the running trace every 10 calls and alarm after several high scores in a row.
  8. Explainability: SHAP, permutation importance and occlusion; attention only as a sanity check.
  9. Robustness and cost: a mimicry test that inserts 10, 20 and 50% benign calls; calibration, inference time and model size.
  10. Statistics: bootstrap confidence intervals and paired tests on the same folds before calling one model better.

Key findings

  • Near-perfect accuracy can be a mirage.On the first version of the dataset every model, even a random forest, scored about 99%. An audit showed much of it came from shortcuts: trace length, a benign set dominated by small GUI utilities, family names that differed only in letter case (LockBit vs lockbit), repeated runs of one binary on both sides of the split, and models given different windows. Finding and controlling these became a core contribution.
  • Counts beat order.The strongest model is gradient boosting on call counts. Sequence models do use order, since shuffling hurts them, but they don't beat a model that ignores it.
  • Early detection is the hard part.Accuracy drops clearly when a model sees only the first few hundred calls, and no model yet reaches 95% recall at 1% false-positive rate within 1,000 calls. I report this as a result rather than hide it.
  • Most unseen families are still caught.Leave-one-family-out recall stays high on average, while a few families such as REvil remain hard, and samples from a completely different source are much harder.
  • The model looks at plausible behaviour.Top features include process creation, file writes and process termination. On Windows 10, process enumeration (CreateToolhelp32Snapshot) appears in 30% of ransomware traces but only 1% of benign ones.

Running thousands of live malware samples on one workstation

The ML only works if the lab behind it does. These are the systems problems I had to solve along the way.

ProblemWhat I did
  • The disk filled repeatedly; each analysis task produced 100 MB or more
    Turned off memory dumps, packet capture and screenshots; extracted traces in chunks of 100 and deleted raw reports; grew the Linux partition from about 150 GB to 450 GB.
  • Long batch runs were interrupted and logs were lost
    Wrote a resumable submitter and a progress checker; derived labels from SHA-256-named folders instead of fragile logs.
  • Over half of ransomware traces were cut off at 1,000 calls
    Raised the cap to 3,000 calls and the run time from 120 s to 240 s.
  • MongoDB broke after a GPU driver install
    Reinstalled MongoDB 4.4 with compatible libraries.
  • Thousands of inconsistent family names across sources
    Built a normalisation and alias table that is applied before any split.
  • LSTM and Transformer training was too slow on a laptop GPU
    Grouped calls into patches of 4 and moved training to Kaggle GPUs.
  • On Windows 10, many 64-bit samples produced no monitored calls
    Diagnosed it by architecture: 64-bit benign programs kept only 9% of traces versus 59% for 32-bit. An improved re-run is planned.

Safety and ethics

All samples are live malware. They are kept only on a dedicated analysis machine and run only inside virtual machines that are reset to a clean snapshot after every run. Malware binaries are never redistributed.

    MiniRedis: a Redis-compatible server in C++17

    An in-memory key-value database server written from scratch with no outside libraries. Real Redis clients, including the official Python client, can talk to it.

    • A multithreaded TCP server that speaks the Redis protocol (RESP2 and RESP3), with a pool of worker threads.
    • Data split into 16 independently locked shards, so clients working on different keys don't wait for each other.
    • O(1) LRU eviction, key expiry through lazy checks plus a min-heap sweeper, and an append-only file that rebuilds the data after a restart.
    • 49 tests pass under ThreadSanitizer, AddressSanitizer and UBSan. About 100,000 requests a second on a 2-core VM with 50 clients.
